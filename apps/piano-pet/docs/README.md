# ピアノペット ドキュメント

ピアノペット（ピアノ練習PWA・猫育成）の要件・設計・機能の文書一覧。

| ドキュメント | 役割 | 読むとき |
|---|---|---|
| [requirements.md](./requirements.md) | 何を・誰のために作るか（目的・利用者・機能要件・非機能要件・スコープ外） | 機能を足す／やめる判断をするとき |
| [features.md](./features.md) | 画面とふるまい・報酬ロジック・アイテム・運用（SW／予算／テスト）。末尾に機能→実装→テストの[トレーサビリティ表](./features.md#トレーサビリティ表) | 挙動を変える・直すとき |
| [data-model.md](./data-model.md) | 状態スキーマ・正規化・マイグレーション・クラウド同期とマージ規則・バックアップ | 保存・同期に触るとき |
| [backlog.md](./backlog.md) | 初期ロードマップ（凍結。以降のバックログは GitHub Issues） | — |

## 更新ルール

- `apps/piano-pet/` のソースを変えたら、**同じPRで requirements.md と該当する文書を更新する**（[CLAUDE.md](../../../CLAUDE.md)）
- モジュール・テストファイルを足した／消したときは、features.md の[トレーサビリティ表](./features.md#トレーサビリティ表)も更新する
- コードのコメントが参照している節名（features.md「記録の動画クリップ演出」「ポップアップ演出」「ねこスタンプちょう」、data-model.md「取り込み経路は3つあり、規則が同じではない」、requirements.md「受容しているリスク」）は、変えるならコード側も直す
- 予算の枠の値と、枠をいつ・なぜ変えたかは [scripts/perf-budget.mjs](../../../scripts/perf-budget.mjs) のコメントが正。文書には現状の表と、設計判断の根拠としての実測値（○→○ KiB）だけを書く

## 書き方

- 各節は **冒頭の1行（Issue・実装・テスト）→ 仕様 → 設計判断** の順に書く
- 仕様には事実だけを書く。理由・経緯・不採用案・実測値は「設計判断」に分ける
- 1文に「事実＋理由＋経緯」を詰めない。事実の列挙は表、手順は番号付きリスト、判断は箇条書き
- 同じ理由を2か所に書かない。片方はリンクにする
